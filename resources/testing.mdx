Before going live, thoroughly test every payment flow in MoneyDev's sandbox environment. The sandbox mirrors the production API exactly — same endpoints, same request and response shapes, same webhook events — but no real money ever moves and no real cards or bank accounts are charged.

## Sandbox vs. Production

MoneyDev uses your API key to determine which environment a request targets. There are two key types:

| Key prefix | Environment | Description |
|---|---|---|
| `sk_test_...` | Sandbox | Safe for development and QA — no real transactions |
| `sk_live_...` | Production | Live traffic — real charges and payouts |

Both key types work against the same base URL (`https://api.moneydev.com.br/v1`). The environment is determined entirely by the key you pass in the `Authorization` header, so you can swap environments without changing a single line of integration code.

## Getting Your Test API Key

Retrieve your sandbox key from the **MoneyDev Dashboard**:

1. Log in at [dashboard.moneydev.com.br](https://dashboard.moneydev.com.br).
2. Navigate to **Settings → API Keys**.
3. Copy the key listed under **Test Keys** — it starts with `sk_test_`.

Store the key in an environment variable (e.g. `MONEYDEV_API_KEY`) and never commit it to source control.

## Test Card Numbers

Use the card numbers below to simulate specific outcomes in sandbox. Any expiry date in the future and any three-digit CVV are accepted.

| Card Number | Brand | Result |
|---|---|---|
| `4111111111111111` | Visa | Approved |
| `5500000000000004` | Mastercard | Approved |
| `4000000000000002` | Visa | Declined (insufficient funds) |
| `4000000000000069` | Visa | Declined (expired card) |
| `6362970000457013` | Elo | Approved |

For 3DS flows, append `?force_3ds=true` to your charge request to trigger an authentication challenge in sandbox.

## Testing PIX Payments

Any PIX payment created in sandbox enters the `pending` status immediately and is **auto-confirmed after 5 seconds**. If you need to confirm it on demand — for example, to test a webhook handler synchronously — call the sandbox simulation endpoint:

```bash
curl -X POST https://api.moneydev.com.br/v1/sandbox/payments/{id}/confirm \
  -H "Authorization: Bearer sk_test_YOUR_KEY"
```

A successful call transitions the payment to `paid` and fires the `payment.paid` webhook event to your registered endpoint.

## Testing Boleto Payments

Boleto payments in sandbox start in `waiting_payment` status. Simulate a bank slip being paid by calling:

```bash
curl -X POST https://api.moneydev.com.br/v1/sandbox/payments/{id}/pay \
  -H "Authorization: Bearer sk_test_YOUR_KEY"
```

This triggers the same state-machine transitions and webhook events that a real boleto payment would produce, letting you verify your fulfillment logic end-to-end.

## Testing Webhooks

Use the **Webhook Tester** built into the MoneyDev Dashboard to fire sample events at any endpoint without creating actual payments:

1. Go to **Developers → Webhooks** in the Dashboard.
2. Select your endpoint from the list.
3. Choose an event type (e.g. `payment.paid`, `payment.refunded`).
4. Click **Send Test Event**.

The Dashboard displays the full request payload, your server's HTTP response code, and any response body — making it easy to debug your handler before receiving real traffic.

<Note>
Sandbox data is completely isolated from production. Objects created with a `sk_test_` key — payments, customers, refunds — are never visible in production and cannot be migrated. Likewise, production data is never accessible from the sandbox.
</Note>

<Tip>
Before switching to your live API key, run through every payment method you plan to offer: at least one successful card charge, one declined card, a PIX confirmation, a boleto payment, and a refund. Cover the unhappy paths too — expired cards, insufficient funds, and duplicate requests — so your error handling is proven before real customers encounter it.
</Tip>
