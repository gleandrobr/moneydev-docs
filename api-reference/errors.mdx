When a `/v1` request fails, MoneyDev returns a `4xx` or `5xx` status and a JSON body with a single `error` object.

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "invalid_customer_id",
    "message": "O ID do cliente é inválido.",
    "param": "customer_id",
    "request_id": "req-a1b2c3d4"
  }
}
```

<ResponseField name="error.type" type="string">
  Broad category of the error. See [types](#error-types) below.
</ResponseField>

<ResponseField name="error.code" type="string">
  A stable, specific machine-readable string, e.g. `customer_email_already_exists`. Branch on this.
</ResponseField>

<ResponseField name="error.message" type="string">
  A human-readable explanation, in Brazilian Portuguese. For end users where helpful, but log it — do not pattern-match on it.
</ResponseField>

<ResponseField name="error.param" type="string">
  Present when the error is tied to one input field. Dotted for nested fields, e.g. `default_offer.amount_minor`.
</ResponseField>

<ResponseField name="error.request_id" type="string">
  Identifier for this request, also returned as the `X-Request-Id` response header. Quote it when contacting support.
</ResponseField>

<Note>
  `POST /oauth/token` does not use this shape. Its failures follow the OAuth spec: `{ "error": "...", "error_description": "..." }`. See [Authentication](/authentication#token-endpoint-errors).
</Note>

## Error types

| `type` | Status | Meaning |
|---|---|---|
| `authentication_error` | `401` | Missing, invalid, expired, or revoked access token |
| `authorization_error` | `403` | The token is valid but lacks the required scope |
| `invalid_request_error` | `400` | Malformed request — bad JSON, failed validation, an unparseable ID or cursor |
| `not_found_error` | `404` | The resource does not exist, or is not visible to your account |
| `conflict_error` | `409` | The request collides with existing state, e.g. a duplicate unique value |
| `api_error` | `500` | Something failed on our side. Safe to retry with backoff |

## Common codes

| `code` | Type | Notes |
|---|---|---|
| `missing_access_token` | `authentication_error` | No `Authorization: Bearer` header |
| `invalid_access_token` | `authentication_error` | Token rejected |
| `insufficient_scope` | `authorization_error` | Token missing the endpoint's scope |
| `invalid_request` | `invalid_request_error` | Schema validation failed; `param` points at the field |
| `invalid_cursor` | `invalid_request_error` | `starting_after` is not a valid ID for this list |
| `customer_email_already_exists` | `conflict_error` | A customer with that email already exists for your account |
| `checkout_external_id_already_exists` | `conflict_error` | `external_id` already used on another checkout |

Resource-specific codes (`customer_not_found`, `offer_not_found`, `recurring_checkout_not_supported`, …) are listed on each endpoint page.

## Validation errors

Request bodies are schema-validated before any work happens. A failure returns `400` with `code: "invalid_request"` and `param` set to the offending field path:

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "invalid_request",
    "message": "body/email must match format \"email\"",
    "param": "email",
    "request_id": "req-a1b2c3d4"
  }
}
```

## Retrying

Retry `500` (`api_error`) and the OAuth `503` (`temporarily_unavailable`) with exponential backoff. Do not blindly retry `4xx` — fix the request first. For safe retries of `POST /v1/checkouts`, set an `external_id`: a repeat with the same value returns `checkout_external_id_already_exists` instead of creating a second session.
